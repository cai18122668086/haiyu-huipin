# Commercial orchestration

Build one machine-checked commercial orchestration contract between product
truth and prompt compilation. Retain the complete v0.1.13 output as evidence,
then execute a page-duty-resolved prompt.

## Required decision objects

- `information_confidence`: classify every selected claim as `CONFIRMED`,
  `REASONABLE_INFERENCE`, or `NEEDS_CONFIRMATION`. Never use the last class as
  visible selling copy.
- `buyer_demand_map`: assign one purchase question to every page.
- `demand_to_selling_point_match`: bind each demand to a lead selling point and
  optional related support. Build one coherent visual story; do not require a
  separate proof panel for every support item.
- `purchase_decision_type`: state the dominant decision logic for the current
  product, such as efficacy/parameter, identity/evidence, or verified value.
- `page_strategy`: state the main resistance, conversion angle, and proof
  progression for the set.
- `page_task_table`: define the six-page selling strategy, not a pixel blueprint.
- `visual_rhythm_plan`: vary subject scale, evidence topology, layout structure,
  reading path, and information density while retaining Campaign Style.

## Six-page control sheet

Every `page_task_table` row must contain: page index and role, buyer demand and
question, a lead claim, optional related support, confidence, a visual idea,
identity evidence, copy direction, risk boundary and difference from the
previous page. Subject scale, layout and camera notes are suggestions that the
executing Agent may improve.

Keep those fields internal. The approval message shows only a concise six-row
summary: concise labels for the main selling point and related supporting
points, one visual-proof phrase,
composition, reading hierarchy, non-repetition reason and commercial closure.
Do not append the complete claim coverage, confidence, deferred-fact or prompt
tables unless the user explicitly asks. Preserve exact user source text only in
the machine-readable fact contract. User facts form an available truth pool;
they are not a requirement to place every sentence on one of six pages. Visible
copy may be shortened or commercially rewritten when meaning, numbers and
conditions remain unchanged.

One image may communicate multiple related selling points. Keep one page duty
and a clear lead hierarchy, but do not convert “page duty” into a one-claim
limit. Across the set, avoid repeating the same bundle, proof object and
conclusion on consecutive pages. Supporting overlap is allowed when its role is
different and visible.

The search listing cover and carousel identity hero are separate commercial
jobs. The search cover must prioritize thumbnail recognition, one verified
click hook, several unequal verified modules when useful, and a commercial closure. The carousel
hero must switch to product identity and editorial Campaign expression. They
must not share a shot/crop, copy topology, subject anchor, reading path, evidence
topology, or complete layout skeleton.

Freeze the complete product identity and one background visual world before
generation. All pages share product geometry, color blocks, packaging layout,
component relationships, color temperature, light direction, background
palette, material language and photography finish. Page layouts and scene
content vary; product identity and background style do not.

## Preservation and conflict-resolution rule

For the default `compile-v013` route, retain the exact v0.1.13 compiled output
as session evidence. Do not send its complete legacy prompts to the image model.
Normalize identity, facts and structured evidence into the v0.1.15 product-
derived quality contract, resolve page duties once, and compile one concise
execution prompt per page. Legacy category defaults may never override current-
product style evidence or user preferences. Legacy keyword counts, literal-copy
gates and layout prescriptions also never override v0.1.17. Resolve conflicts
by discarding the conflicting legacy instruction, not by stacking another
prompt envelope or writing a larger manual contract.

## Execution boundary

The orchestration contract becomes part of the compiled hash. `generate-next`
must emit only the current page task, original-evidence allowlist, revision,
compiled hash, generation token and square output contract. Record the
resulting file and audit its actual pixels before permitting the next page.

One explicit user authorization covers the approved six-page plan and
fact-preserving targeted repairs. A local repair or Agent pixel-reviewed style
calibration rebases the generation token automatically. A full campaign replan
still invalidates authorization and requires user confirmation.

## Legacy compatibility boundary

Normalize v0.1.17 reference objects to pure image-path strings before entering
the preserved v0.1.13 compiler. Keep all identity description in the separate
identity contract. The legacy “one or two emphasized keywords” gate controls
only how many phrases receive dominant typographic emphasis; it does not limit
the number of eligible selling points and does not require every eligible fact
to appear. Resolve adapter conflicts internally inside the v0.1.17 route; do
not narrate them and do not create a giant manual fallback contract.
