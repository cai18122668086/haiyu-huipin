# Advanced page archetypes

Use these archetypes when an ordinary hero, scene, structure, data, or specification screen cannot make the buyer's decision visible. They are reasoning patterns, not fixed layouts or required pages.

## Cross-category campaign library

Use this common library for every category; category adapters choose candidates and evidence forms, never fixed screen counts:

- `PAIN_SCENE`: affected person/object/environment + undesired state/action + consequence.
- `PAIN_TO_SOLUTION_BRIDGE`: problem state visibly transitions toward the current product's verified value bridge.
- `BENEFIT_OVERVIEW`: several primary benefits are introduced with distinct zones; this is overview, not dedicated depth.
- `DEDICATED_BENEFIT_PROOF`: one primary claim leads and its claim object, action or result is the dominant visual; the product may be supporting or absent.
- `SOURCE_ACTION_RESULT`: verified source/component -> action/path -> result.
- `WHOLE_PLUS_MACRO`: full product plus a material/component/texture detail at a second scale.
- `ACTION_SEQUENCE`: ordered handling, installation, preparation, use or maintenance action.
- `USE_SCOPE_MATRIX`: different people/tasks/scenes mapped to a verified common benefit.
- `STATE_CONTRAST`: truthful before/after or condition A/B under a stated basis.
- `SENSORY_WORLD`: visualized texture, aroma, feel, sound or atmosphere without inventing efficacy.
- `SELECTION_COMPARISON`: buyer condition -> differentiating attribute -> suitable option.
- `TRUST_EVIDENCE`: documented evidence tied to the conclusion it supports, never a certificate wall.
- `PURCHASE_CLOSURE`: complete product, core benefits and audience/use return as the final commercial memory.

For six or more modules, use at least four archetypes and never repeat one archetype three screens in a row. Archetype variation must change the meaning-bearing relation, not merely the background.

## Routing rule

Choose an archetype only after establishing:

`buyer doubt -> verified evidence -> visible relation -> page duty`

Do not choose one because a reference page looked impressive. If the current product lacks the required evidence, downgrade to a truthful action, scene, product-detail, or concise factual screen.

## Conceptual claim-object transformation

Use when a verified claim concerns an object or effect that cannot be photographed directly but should still be visually understood.

- Required relation: recognizable claim object -> visible contact/path/state change -> reduced, separated, removed, blocked or resolved end state.
- The claim object and change occupy the first visual rank; headline and packshot cannot replace them.
- The product may be absent. Preserve product binding through the approved claim, campaign visual DNA, adjacent module sequence and truthful action/result language.
- Use stylized commercial illustration or non-diagnostic 3D visualization. Do not imitate laboratory microscopy, exact biological anatomy, a measurement UI or test footage.
- When the evidence ceiling is packaging-only, the visualization illustrates claim meaning but does not prove mechanism, percentage, duration or test conditions.

## Directed pathway

Use when value depends on where heat, water, air, force, signal, material, or dirt travels.

- Required relation: source or entry -> intermediate nodes -> contact/working zone -> visible result.
- Show direction, sequence, coverage, and the product component that anchors each node.
- Use a section, transparent diagram, traced macro, or staged process only when the structure is verified. Otherwise label it as an illustration and avoid photorealistic internal anatomy.
- Bind each annotation to a path node. Decorative arrows without an origin and destination do not prove mechanism.

## Trigger–feedback–result interaction

Use when the buyer needs to understand control, sensing, adjustment, automation, or mode switching.

- Required relation: user/environment trigger -> device state or feedback -> resulting action/value.
- Keep the control, feedback signal, and affected product behavior in one readable chain.
- Distinguish a verified interface from a conceptual UI. Never invent an app screen, indicator state, automation, or sensor response.
- Prefer hand action, state contrast, or a short sequence over a detached interface screenshot.

## Installation and fit

Use when purchase risk depends on physical fit, clearance, connection, drainage, power, mounting, reach, or maintenance access.

- Required relation: installation space -> product dimensions/orientation -> connection or clearance -> usable final state.
- Show the real installation envelope, not only a dimension table.
- Separate installation evidence from lifestyle aspiration when merging them would hide engineering constraints.
- Preserve exact dimensions and conditions. If they are missing, show only generic placement context and mark backend/manual confirmation as required.

## Selection matrix

Use when variants, modes, accessories, programs, sizes, colors, or people must be matched to a task.

- Required relation: buyer condition or task -> differentiating attribute -> recommended choice.
- Arrange options by a single decision axis per visual group. An unexplained product lineup is not a selection tool.
- Use the same comparison conditions, scale, and label logic across options.
- Keep color-only choice separate from functional choice unless both truly affect the purchase decision.

## Planning record

For any advanced archetype, record:

- buyer question;
- verified evidence and its source;
- start/end states or compared conditions;
- visual carrier and visual verb;
- composition family and camera;
- minimum copy needed to prevent a false inference;
- downgrade route if evidence is insufficient.

## Failure conditions

Reject the archetype when it:

- depends on an unseen internal structure or invented result;
- uses arrows, icons, UI, dimensions, or certificates as decoration rather than a readable relation;
- combines several independent mechanisms without one lead conclusion;
- duplicates an adjacent screen's duty, carrier, camera, and text mode;
- would still communicate the same thing after replacing the current product with a generic packshot.
